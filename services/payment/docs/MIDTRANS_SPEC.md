# Midtrans Integration Specification

This document details the specific **Core API** endpoints and JSON payloads required to integrate the Payment Service with **Midtrans**.

## 1. Overview & Credentials

We use the **Core API** (Server-to-Server) rather than Snap Redirect for most methods to maintain a Custom UI.

*   **Documentation**: [Midtrans Core API Docs](https://docs.midtrans.com/reference/core-api-overview)
*   **Base URL (Sandbox)**: `https://api.sandbox.midtrans.com`
*   **Base URL (Production)**: `https://api.midtrans.com`
*   **Authentication**: Basic Auth
    *   **Username**: `<Server_Key>` (from `payment_gateway_configs` table)
    *   **Password**: `<Leave Blank>`
    *   **Header**: `Authorization: Basic base64(ServerKey + ":")`

---

## 2. Inbound Data (From Config, Not API)

**Q: How do we get the list of available payment methods?**

Midtrans **does not** provide a runtime API to fetch "Enabled Payment Methods" for Core API integrations.
*   **Strategy**: We must manually define these in our `payment_methods` database table.
*   **Configuration**: The Admin must toggle methods (e.g., BCA VA, GoPay, CC) in the YBB Dashboard to match what is enabled in the Midtrans MAP Dashboard.

## 3. Outbound Calls (Payment Service -> Midtrans)

These calls happen inside the `POST /api/v1/intents/{id}/confirm` handler.

### 3.1. Create Transaction (Charge)
The primary endpoint to initiate any payment.

*   **Endpoint**: `POST /v2/charge`
*   **Common Body**:
    ```json
    {
      "transaction_details": {
        "order_id": "txn_uuid_v4", // Our PaymentTransaction.id
        "gross_amount": 150000     // Matches PaymentIntent.amount
      },
      "customer_details": {
        "first_name": "Hendra",
        "email": "user@example.com" // From User Service
      }
    }
    ```

#### Variant A: Credit Card (Authorisation)
Requires `token_id` generated by Frontend via Midtrans.js.

*   **JSON Merge**:
    ```json
    {
      "payment_type": "credit_card",
      "credit_card": {
        "token_id": "tok_123456", // Passed from Frontend
        "authentication": true    // 3DS is active
      }
    }
    ```
*   **Response**: Check `status_code`. If `200` and `transaction_status` is `capture` (or `success` for non-3DS), it's done. If `redirect_url` is present (3DS), send to Frontend.

#### Variant B: Bank Transfer (Virtual Account)
Directly returns the VA number.

*   **JSON Merge**:
    ```json
    {
      "payment_type": "bank_transfer",
      "bank_transfer": {
        "bank": "bca" // or "bni", "permata"
      }
    }
    ```
*   **Response**:
    ```json
    {
      "status_code": "201",
      "transaction_status": "pending",
      "va_numbers": [{ "bank": "bca", "va_number": "12345678901" }]
    }
    ```

#### Variant C: E-Wallet (GoPay / QRIS)
Returns a QR code URL or DeepLink.

*   **JSON Merge**:
    ```json
    {
      "payment_type": "gopay" // or "qris"
    }
    ```
*   **Response**:
    ```json
    {
      "status_code": "201",
      "actions": [
        { "name": "generate-qr-code", "url": "https://api.midtrans.com/..." },
        { "name": "deeplink-redirect", "url": "gojek://..." }
      ]
    }
    ```

### 3.2. Check Transaction Status
Used by our Polling Worker (Chronos) to reconcile `PENDING` transactions if Webhook is missed.

*   **Endpoint**: `GET /v2/{order_id}/status`
*   **Response**: Returns the standard Transaction Status Object (same as Webhook).

### 3.3. Expire Transaction
Used when the Program Schedule passes or the User manually cancels.

*   **Endpoint**: `POST /v2/{order_id}/expire`
*   **Purpose**: Indexes the VA so user can no longer pay. Use this instead of Cancel for VAs.

### 3.4. Cancel Transaction
Used for Credit Cards (Pre-Settlement) or Pending E-Wallets.

*   **Endpoint**: `POST /v2/{order_id}/cancel`

## 4. Inbound Calls (Midtrans -> Payment Service)

### 4.1. Webhook Notification
Midtrans sends a POST request to the URL configured in MAP Dashboard.

*   **Flow**: Midtrans -> Payment Service (`/api/v1/payments/webhook/midtrans`).
*   **Payload**:
    ```json
    {
      "transaction_time": "2026-01-23 14:55:00",
      "transaction_status": "settlement", // or 'capture', 'pending', 'expire', 'deny'
      "transaction_id": "mid_txn_123",
      "status_message": "midtrans payment notification",
      "status_code": "200",
      "signature_key": "SHA512(...)",
      "payment_type": "credit_card",
      "order_id": "txn_uuid_v4", // Matches Our PaymentTransaction.id
      "gross_amount": "150000.00",
      "fraud_status": "accept" // Important for Cards
    }
    ```

### 4.2. Security Verification (Crucial)
Before trusting the Webhook, we **MUST** verify the `signature_key`.

*   **Formula**:
    ```
    Hash = SHA512(order_id + status_code + gross_amount + ServerKey)
    ```
*   **Logic**:
    1.  Get `ServerKey` for the `PaymentTransaction`'s config.
    2.  Concatenate string.
    3.  Hash it.
    4.  Compare with `payload.signature_key`.
    5.  If mismatch, **ignore** (Possible Spoof).

## 6. Error Handling

*   **400 Bad Request**: Validation error (e.g., Invalid Bank Code). Fail the Transaction immediately.
*   **401 Unauthorized**: Server Key is wrong. Critical Config Error.
*   **406 Not Acceptable**: The specific payment channel is disabled for this account.
*   **5xx Server Error**: Midtrans down. Keep Transaction `PENDING` and retry later.
