# Payment Service API Specification & Contract

## 1. Interaction Model (The "3-Tier" Flow)

This document defines the strict contracts between the three key players in the payment lifecycle.

```mermaid
graph LR
    FE[FrontEnd (Next.js)] -- "Public HTTPS (Auth: Bearer Token)" --> API[Main API Service]
    API -- "Internal HTTP/gRPC (Auth: Service Key)" --> PAY[Payment Service]
  GW[Payment Gateway] -- "Public HTTPS Webhook" --> PAY
```

*   **Public API**: Exposed to the internet, consumed by Next.js clients. Secured by User Session (JWT).
*   **Internal API**: Exposed ONLY within the private network (VPC/Cluster). Consumed by the API Service. Secured by mTLS or Internal Service Keys.

---

## 2. Public API Contract (Consumed by Frontend)

**Base URL**: Frontend requests are handled by the Main API Service, not the Payment Service directly.
**Authentication**: `Authorization: Bearer <User_JWT>`

### 2.1. Get Payment Methods
Used to render the "Select Payment Method" screen.

*   **Endpoint**: `GET /methods`
*   **Query Params**:
    *   `program_id` (optional): To filter methods available for a specific program.
*   **Success Response (200 OK)**:
    ```json
    {
      "data": [
        {
          "id": "pm_12345",
          "code": "manual_bca",
          "name": "Bank Transfer BCA",
          "type": "MANUAL",
          "logo_url": "https://assets.ybb.com/bca.png",
          "is_enabled": true
        },
        {
          "id": "pm_67890",
          "code": "midtrans_card",
          "name": "Credit Card",
          "type": "AUTOMATIC",
          "provider": "midtrans",
          "logo_url": "https://assets.ybb.com/visa.png",
          "is_enabled": true
        }
      ]
    }
    ```

### 2.2. Create Payment Intent
Called when the user enters the "Checkout" page or clicks "Proceed".

*   **Endpoint**: `POST /intents`
*   **Request Body**:
    ```json
    {
      "amount": 150000,
      "currency": "IDR",
      "metadata": {
        "program_id": "prog_123",
        "tier_id": "tier_gold",
        "application_id": "app_999"
      }
    }
    ```
*   **Success Response (201 Created)**:
    ```json
    {
      "data": {
        "id": "pi_uuid_v4",
        "status": "REQUIRES_PAYMENT_METHOD",
        "amount": 150000,
        "expiration_at": "2026-01-24T10:00:00Z"
      }
    }
    ```

### 2.3. Confirm Payment (Attempt to Pay)
Called after the user selects a method (and optionally tokenizes their card).

*   **Endpoint**: `POST /intents/{id}/confirm`
*   **Headers**:
    *   `Idempotency-Key`: `uuid-v4` (Generated by Frontend)
*   **Request Body**:
    ```json
    {
      "payment_method_id": "pm_12345",
      "gateway_token": "tok_midtrans_123" // Optional. Required for Credit Cards.
    }
    ```
*   **Scenario A: Automatic (Redirect/VA)**
    ```json
    {
      "data": {
        "status": "PROCESSING",
        "action": {
          "type": "redirect",
          "url": "https://app.midtrans.com/snap/v2/vtweb/..."
        }
      }
    }
    ```

### 2.4. Upload Proof (Manual Only)
*   **Endpoint**: `POST /transactions/{id}/proof`
*   **Request Body**:
    ```json
    {
      "file_url": "https://storage.ybb.com/proofs/user_1/txn_123.jpg"
    }
    ```
*   **Success Response (200 OK)**:
    ```json
    {
      "data": {
        "status": "NEEDS_REVIEW",
        "message": "Proof uploaded successfully. Waiting for admin approval."
      }
    }
    ```

## 3. Internal Service Interface (API -> Payment)

This contract governs how the **Main API Service** talks to the **Payment Domain Service**.

**Protocol**: HTTP REST (JSON)
**Network**: Private VPC for operational APIs. Only the gateway webhook endpoint is exposed publicly.
**Content-Type**: `application/json`

### 3.1. Security & Authentication
Since this is an internal communication, we use valid Service-to-Service authentication to prevent accidental access.

*   **Header**: `X-Internal-Service-Key`
*   **Value**: A shared secret (ROTATING_API_KEY) stored in Environment Variables / Secrets Manager.
*   **Behavior**: Payment Service middleware **MUST** reject any request without this exact key with `401 Unauthorized`.

### 3.2. Resilience Standards (Timeouts)
Payments are sensitive. We cannot wait forever.

*   **Connect Timeout**: 2 seconds (Fast check if service is up).
*   **Read Timeout**: 10 seconds (Gateways can be slow).
*   **Retry Policy**:
    *   **On 5xx Errors**: Retry 3 times with specific backoff (1s, 2s, 4s).
    *   **On 4xx Errors**: DO NOT Retry (Business logic error).

### 3.3. Shared Types & Enums
Both services must agree on these values (Protobuf or Shared Go Structs recommended).

*   **PaymentStatus**: `PENDING`, `SUCCESS`, `FAILED`, `EXPIRED`.
*   **Currency**: ISO 4217 Code.

### 3.4. Endpoints (Payment Service Internal API)

#### `POST /api/v1/intents`
Orchestrated by Facade API.
*   **Input**:
    ```json
    {
      "user_id": "uuid",
      "amount": 10000,
      "metadata": { ... }
    }
    ```
*   **Output**: Returns the raw `PaymentIntent` object.

#### `POST /api/v1/intents/{id}/confirm`
The Main API forwards the user's confirmation to the Payment Service to trigger the Gateway Charge.
*   **Input**:
    ```json
    {
      "payment_method_id": "pm_12345",
      "gateway_token": "tok_midtrans_123" // Optional matches Public API
    }
    ```
*   **Output**: Result of the charge (same structure as Public API 2.3).

#### `GET /api/v1/payments/{id}`
Returns either a transaction record or an intent record with embedded transactions.

#### `GET /api/v1/payments/user/{userId}`
Returns a paginated list of payment intents with embedded transactions.

#### `POST /api/v1/payments/webhook/{gateway}`
This route is called directly by Midtrans or other gateways. It is the only Payment Service route that should be publicly reachable.

### 3.5. Error Handling Contract

The Payment Service will return errors in this standardized format so the API Service can map them to Frontend-friendly messages.

```json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "The card has insufficient balance.",
    "upstream_code": "411" // Code from Midtrans/Xendit
  }
}
```

*   **402 Payment Required**: Logic errors (Card declined, Insufficient Funds).
*   **409 Conflict**: Idempotency violation.
*   **429 Too Many Requests**: Rate limiting from the Gateway.
*   **503 Service Unavailable**: Gateway is down. API Service should queue or retry.

## 4. Frontend Developer Checklist

1.  **Generate UUIDs**: Make sure you generate a unique `Idempotency-Key` UUID for every *click* of the Pay button.
2.  **Handle 3DS**: If the response `action.type` is `redirect`, open it in a popup or new tab. Don't block the UI.
3.  **Polling**: If status is `PROCESSING`, poll `GET /intents/{id}` every 3-5 seconds until it becomes `SUCCEEDED` or `FAILED`.
4.  **Error Mapping**: Display `error.message` directly to the user if it's a 4xx error.

## 5. Backend Developer Checklist

1.  **Ingress Rules**: Keep all Payment Service routes private except `/api/v1/payments/webhook/:gateway`.
2.  **Facade Pattern**: The `API Service` should simple passthrough requests but **MUST** inject the `user_id` from the JWT into the Internal Request body (Trust boundaries).
3.  **Webhook Verification**: Validate the gateway signature in the Payment Service before updating records.
4.  **Circuit Breaker**: If Payment Service is down, fail fast.
