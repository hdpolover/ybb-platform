## Decisions (the why, not just the what)

**Item 7 is LATENT, not currently firing — fixed anyway.** Prod check showed all 6 live brands have
exactly one `isPublished && isActive` program, and MEYS 2027 is back to `draft`/inactive. The bug
fires the moment an admin publishes next year's program to prepare it: rule 1 orders by `year DESC`,
so the future program steals every read path from the one actually taking registrations. Fix is
**rule 0** on the shared resolver — published+active AND registration currently open (NULL open/close
= unbounded, matching every other registration gate). Purely additive: it only changes the outcome
when 2+ programs pass rule 1, which is exactly the broken case.

**`get-auth-context.handler.ts` reuses `openRegistrationProgramQuery` ALONE, not `resolveActiveProgram`.**
The full resolver's rule-2 fallback would hand a program to brands that correctly resolve to `null`
at the registration entry point. The previous handoff said "do not repoint it" — that still holds for
the *full* resolver. Do not "simplify" this later.

**Item 1 was never a cache bug.** Invalidation is fully wired across all three layers. The real cause:
`program?.logoUrl || brand.logoUrl` precedence (`settings.strategy.ts:110`), and Istanbul's
`programs.logo_url` held a **byte-identical copy** of the brand logo — overriding nothing, but
permanently pinning the public site to a stale URL so every brand-level edit was a silent no-op.
China and Middle East have genuinely distinct program logos: those are real overrides, left alone.

**Item 8's audit found 2 more leak sites than reported.** Beyond exports and the LoA recipient query,
`submission-deadline-reminder.service.ts` and `payment-reconciliation.service.ts` had the same gap.
One shared predicate (`shared/utils/active-participant.filter.ts`) spread into all four, not four
copies. Payment reconciliation still *reconciles* a deactivated user's invoice (money must reconcile
either way) — only the reminder email is gated. Admin browse/detail views deliberately left
unfiltered so history stays visible, per the requirement.

**`BrandEditPage` was NOT dead code — do not delete it.** Instinct said delete; evidence said
otherwise. It is the ONLY UI for banner upload, the `requireEmailVerification` toggle, and Meta CAPI
credentials. Now reachable via an "Advanced Edit" button on `BrandDetailPage`.

**The two `prisma-tx-mock.ts` helpers were two different APIs sharing one path**, not one file
diverged. `createPrismaTxMock(buildModels)` (dev) vs `makePrismaTxMock(prismaShape, txShape)` +
`assertDisjointMocks` + `expectNoOuterWrites` (branch). Both had live callers. Unified by keeping
both exports and making `createPrismaTxMock` **delegate** to `makePrismaTxMock` — so the 11 existing
copier specs now inherit the disjointness assertion for free (and still pass, which proves their
`buildModels` returns fresh objects).

**Item 10 — the write and read paths were exactly inverted.** Reported as "logo dan web banner yang
aku upload belum muncul" on Korea Youth Summit's Media Library (0 files shown). The uploads always
worked: the files were in the file service DB, `status='READY'`, correct `program_id`. They carried
the WRONG `brand_id`.

- **Write was too strict.** `files.controller.ts` (`requestUploadUrl`, `getPresignedUploadUrl`,
  `markFileReady`) discarded the client's `brand_id` and forced `user.brandId` from the JWT, under a
  comment "never trust caller-supplied user_id/brand_id". Correct for `user_id`, WRONG for
  `brand_id`: an admin's JWT carries ONE home brand. `super@ybbhub.com`'s home brand is **China Youth
  Summit**, so every upload that account made for any other brand's program was stamped China.
- **Read was too loose.** `admin-media.controller.listMedia` took `@Query('brand_id')` as-is with no
  authorization, passed to a hard equality filter in the file service
  (`file_repository.py:61-66`: `{program_id, brand_id, is_deleted, status:'READY'}`). Any
  authenticated admin could read another brand's media by pairing a foreign programId with a foreign
  brand_id.

Fix for both is one principle: **derive `brand_id` server-side from the program**, never from the JWT
and never from the request. Authorization reuses the existing
`resolveRevenueAccessScope`/`assertProgramAccess` pair from the revenue module — no new permission
system.

**`markFileReady`'s brand check had to be dropped, and that is safe.** Once uploads correctly stamp
the program's brand, a multi-brand admin's JWT brand legitimately differs from the file's brand, so
the old `file.brand_id != command.brand_id` AND-check would have rejected their own valid uploads.
`user_id` was always the real ownership credential; brand was defense-in-depth. Removing brand only
loosens the case where the caller IS the uploader but their home brand differs. You still cannot mark
another user's file ready.

**`uploadMedia`/`deleteMedia` had the same defect class and were fixed too, beyond the original
scope.** `uploadMedia` read BOTH `brand_id` and `user_id` from the request body — identity spoofing,
not just mis-attribution. `deleteMedia` scoped a destructive call solely on a caller-supplied
`brand_id`, so any admin could delete another brand's file by naming its brand. Leaving these would
have been the "patch only the path the ticket names" failure mode.

**The NULL-`program_id` rows were deliberately NOT backfilled and do not need to be.** Korea's 104
such rows were all uploaded on a single day (2026-05-31) with no `asset_type` — a bulk migration
import, same signature as Japan (114) and WYF (59). MEYS (463) and Istanbul (332) NULL-program rows
span Apr-Aug with no asset types and look like participant documents. None are the client's uploads.

## Traps that cost real time this session — do not relearn

- **NEVER `git add -A` while subagents are working in the same checkout.** Cost the most time this
  session: two agents' uncommitted files were swept into my commits. Either dispatch agents with
  `isolation: "worktree"` (do this) or `git add` explicit paths. Recovery: don't rewrite history
  while a writer is still live; rebuild from base with `git checkout <bad-branch> -- <your files>`,
  then verify with BOTH a filename comparison and a blob-hash comparison before deleting anything.
- **`enableImplicitConversion: true` makes `Boolean("false") === true`.** For a DTO field typed plain
  `boolean`, TS emits `design:type: Boolean` and the ValidationPipe converts the raw string BEFORE
  any `@Transform` runs. Workaround: type the field `boolean | string` (emits `Object`, skipping
  implicit conversion) plus a strict `=== true` check in the handler. Applies to ANY boolean over
  multipart or query string. Always test with the literal string `"false"`.
- **A subagent's "N pre-existing failures" claim may be an artifact of its own broken environment.**
  This happened TWICE this session — both agents reported 3 pre-existing `bootstrap/*-consumer.module`
  failures that do not exist (one worktree had no `node_modules`, the other lacked `dist/protos` and
  `JWT_SECRET`). The real checkout was clean both times. **Always re-run the full suite in the main
  checkout before believing or repeating a failure claim.** Note the inverse also happens: the file
  service's 5 `test_pdf_generator_loa.py` failures WERE genuinely pre-existing (verified on `dev`),
  so don't dismiss every such claim either — check.
- **A cross-service change has a deploy ORDER dependency, and Dokploy gives you no control over it.**
  The item 10 fix spanned `services/api` and `services/file`, which are SEPARATE Dokploy apps
  (`ybb-platform-api-yeghdi-*` and `ybb-platform-file-ucvdu8`). Had the new API deployed first, it
  would have stamped the program's brand while the old file service still enforced
  `file.brand_id != command.brand_id` on mark-ready, silently failing EVERY upload into a stuck
  PROCESSING state. It happened to land file-service-first (14:09) then API (14:12) — luck, not
  design. For the next cross-service change, verify both semantically and be ready to roll forward
  fast.
- **A subagent's failed build may also be a worktree artifact.** Turbopack rejects a symlinked
  `node_modules` that points outside its project root. The admin build was clean in the main checkout.
- **`git cherry -v <upstream> <branch>` compares by patch-id** — use it, not SHA ancestry, to decide
  whether squash-merged branches are safe to delete.
- **Verify a deploy by a semantic signal, then wait for health.** A container that is `Up 17 seconds`
  is not serving yet; `/v1/health` returned connection-refused before returning 200. Port is **4000**,
  path `/v1/health`. Do not declare success on the refused check.
- Several redis containers share the host. The platform's is
  `ybb-platform-redis-service-omv9vw.1.*` (name has a swarm suffix — match with a `grep '^ybb-platform-redis-service-omv9vw'`).
  `ybb-redis` is a decoy, same as the `ybb-postgres` decoy.
- **Full `AppModule` bootstrap fails in the prod container** (a gRPC client cannot start), so the
  documented "compile TS, scp, docker exec node" recipe does NOT work for scripts that need the Nest
  context. Either read the compiled `dist` to replicate what a service does, or drive the layers
  directly (psql + redis-cli + curl).
- Previous handoff's traps all still apply: `npm run lint` in `services/api` is `eslint --fix` and
  MUTATES the tree (use `npx eslint`); two tsconfigs (`build:seed` covers `prisma/seeds/**`);
  `npx jest | tail` returns tail's exit code; commit before injecting to prove a test.

## The recurring defect class — still holding

*A value is silently lost because one layer does not carry what the layer beside it writes.*

This session's instances: the deactivation predicate present in the schema but honored by NO read
path (#13); the `"false"` string inverted by the pipe before the transform could see it (#14); a
program logo column shadowing a brand logo column with no UI surfacing the conflict (#15); and the
sharpest one yet — a guard that hard-forced `brand_id` from the JWT on write while the matching read
accepted `brand_id` from the query string unchecked (#16). **The same field, guarded too hard at one
layer and not at all at the layer beside it.**

**When you add a guard, ask which layer it does NOT cover — and whether the guard is even asking the
right question.** "Never trust caller input" was the right instinct for `user_id` and the wrong one
for `brand_id`: the fix was not to trust the caller, but to derive the value from the resource.
