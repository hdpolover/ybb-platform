## ⚠️ Incident — 2026-07-15 05:10–05:44 UTC

**What broke:** Checkout returned HTTP 500 for any user who already had an open payment intent.

**Root cause — the same bug this whole document is about.** The find-or-create logic went into `CreateIntentHandler` (`internal/application/commands/handlers/create_intent_handler.go`). **Nothing calls that handler on the live path.** `PaymentGrpcServer` (`internal/infrastructure/grpc/server.go:28-56`) holds only repositories — there is no `createIntentHandler` field. gRPC `CreateIntent` (line 58) builds the entity with `entities.NewPaymentIntent(...)` and calls `s.intentRepo.Create(ctx, intent)` **directly**, bypassing the application layer entirely.

So: the handler's reuse logic never ran. But the repository-level 23505 → `ErrDuplicateOpenIntent` translation *did* ship, and `server.go:110-112` wraps any `Create` error as `codes.Internal`:

```go
if err := s.intentRepo.Create(ctx, intent); err != nil {
    return nil, status.Errorf(codes.Internal, "failed to create intent: %v", err)
}
```

Result: the new unique index correctly rejected a duplicate insert → bare error path → `codes.Internal` → NestJS → **HTTP 500 to the user**. The index worked exactly as designed; nothing was there to catch it.

**Why tests didn't catch it:** all 7 new tests exercise `CreateIntentHandler`, which is dead code on the live path. The code was verified; the *path* was not. Note `internal/presentation/http/handlers/` **is** wired to the handler — but open thread #3 already established the HTTP confirm route has no callers.

**Impact:** 3 `CreateIntent` calls in the 34-minute window. 1 succeeded (no prior open intent), 2 failed — both the same user (invoice `e22aadbc`, 05:43:58 and 05:44:02). She retried at 05:49:19 after the rollback and succeeded. Blast radius was small only because traffic was light; 411 open intents were eligible to hit it.

**Mitigation applied:** `DROP INDEX idx_payment_intents_one_open_per_reference;` at ~05:44:30. Inserts immediately succeeded again. Migration 019 remains recorded in `schema_migrations`, so a restart will **not** recreate the index. No data was lost — the 293 soft-deleted rows from 019's dedupe are still soft-deleted and still recoverable.

**Current production state:**
- Code: `80f6e45` deployed. Find-or-create present but unreachable. 23505 translation present but nothing triggers it (index is gone).
- Data: deduped (293 soft-deleted), no unique index, duplicates accumulating again.
- Behaviour: identical to pre-`80f6e45`, i.e. the original duplicate-intent bug.

**To fix forward properly:**
1. Wire `CreateIntentHandler` into `PaymentGrpcServer` (add the field, construct it in `cmd/server/main.go`, call `Handle` from `CreateIntent` instead of touching `intentRepo`). The handler logic and its tests are already correct — they just need to be on the live path.
2. Re-add the index as **migration 020** (019 is burned — already recorded as applied).
3. **Verify against the gRPC path**, not the handler. A passing unit test proved nothing here. Watch `docker logs ybb-prod-payment` for a real `CreateIntent` on an invoice that already has an open intent, and confirm it returns the existing intent with no 23505 and no `codes.Internal`.
4. Consider whether `server.go:110` should map `ErrDuplicateOpenIntent` to something other than `codes.Internal` as defence in depth.

**Lesson for whoever picks this up:** this repo has two presentation layers (`internal/presentation/http` and `internal/infrastructure/grpc`) with **duplicated business logic**. The HTTP layer delegates to `application/commands/handlers`; the gRPC layer reimplements inline against repositories. `confirm_intent_handler.go:59` guards `intent.Status == SUCCEEDED`; the gRPC `ProcessPayment` (lines 158-573) has **no such guard**. Any fix must state which layer it targets and prove it on the live one. **The live one is gRPC.**

**Design note — this differs from the original plan in this doc.** Find-or-create went into **Go's `CreateIntent`**, not the NestJS handler, and no client-generated key was needed. Result: NestJS and `ybb-program-next` are untouched, the logic lives in one place, and the DB unique index is the race guard. The A/B fork described in *Open threads #1* is therefore mostly resolved — A was implemented, server-side only.

**Why the race guard is a repo-level translation:** `cmd/server/main.go`'s `connectDatabase` does not set `TranslateError: true`, so `gorm.ErrDuplicatedKey` never fires — the raw `*pgconn.PgError` comes through. Detection lives in the repository (matching the existing `FindByID` → `ErrPaymentNotFound` convention) so the application layer stays free of gorm/pgconn imports.

## Findings

### 1. The idempotency system is fully implemented and completely unreachable

The Go implementation is genuinely correct — this is not the problem:

- `internal/domain/services/idempotency.go` — SHA-256 request hashing, conflict detection on resource/hash mismatch, in-progress detection.
- `internal/infrastructure/grpc/server.go:158-195` — full flow in `ProcessPayment`: find by key → validate → replay stored response if completed → return stored error if failed → create with DB unique constraint as the race guard.
- `server.go:575` `grpcIdempotencyKey(ctx)` reads `idempotency-key` / `x-idempotency-key` from gRPC metadata.
- `internal/presentation/http/handlers/intent_handler.go:101` reads the `Idempotency-Key` HTTP header.

**It has never executed once in production.** `payment_idempotency_keys` has **0 rows** against 1215 intents / 264 succeeded payments.

Cause: the only production caller never sends the key.
`services/api/src/modules/payments/infrastructure/services/payment-grpc.client.ts:47` — the `metadata()` builder adds `x-internal-service-key` and nothing else. The sole occurrence of the word "idempotency" in that file is a code comment about conflict errors.

`payment_service.proto` has no idempotency field either, but **that does not matter** — gRPC metadata is out-of-band, so no proto change is needed. The server already reads it correctly.

### 2. Wiring the key alone would be a second no-op — the real bug is duplicate intents

`services/api/src/modules/portal/application/commands/handlers/confirm-portal-payment.handler.ts:167` calls `createIntent` on **every** confirm, with no check for an existing intent on the invoice.

So every click mints a fresh `intent_id`. The Go idempotency scopes its resource to `intent_id`. Two clicks = two different resources = **no dedup even with the key wired**.

Production evidence:

```sql
SELECT count(*) AS intents, count(DISTINCT reference_id) AS distinct_refs FROM payment_intents;
--  1215 intents | 801 distinct refs   → 414 surplus intents

SELECT count(*) FROM (
  SELECT reference_id FROM payment_intents GROUP BY reference_id HAVING count(*)>1
) s;
--  186 invoices have more than one intent

SELECT reference_id, count(*) AS intents,
       count(*) FILTER (WHERE status='REQUIRES_PAYMENT_METHOD') AS abandoned,
       count(*) FILTER (WHERE status='SUCCEEDED') AS succeeded
FROM payment_intents GROUP BY reference_id ORDER BY 2 DESC LIMIT 5;
--  worst: one invoice with 12 intents (11 abandoned, 1 paid)
--         another with 11 intents and 0 payments
```

The 700 `REQUIRES_PAYMENT_METHOD` rows are largely not abandoned checkouts — they're repeat clicks.

**Why this hasn't caused a double-charge yet:** the gateway redirect serializes it. Users get bounced to Midtrans/Xendit and only complete the flow once. That's incidental protection, not designed protection. Checked for actual double-charges — the only invoice with 2 SUCCEEDED intents has them **11 days apart** (2026-05-22 and 2026-06-02), which is a legitimate second payment, not a retry artifact.

### 3. Money is `float64` end-to-end

- `Amount float64` on domain entities; DB columns are `numeric(12,2)` / `numeric(15,2)`.
- The proto does it **right** — `int64` minor units — then `server.go:98` casts straight to `float64(req.Amount)`. That cast is the corruption point.
- `toIDR(amount, rate float64) float64` (`server.go`, bottom) does `math.Round(amount * rate)` in float.

Production state:
- **0 rows** currently have non-integer `amount` → **migration to `int64` minor units is lossless today.** That window closes the first time someone pays $10.50.
- **83 rows** already have fractional `fee_provider` and `net_amount` → float arithmetic is live, not theoretical.
- Currency spread: USD 1158 intents ($10–$410), IDR 57 intents (175,800–277,500).

### 4. ~~`exchange_rate` is NULL on all 1215 rows — audit gap~~ — **RETRACTED, this was wrong**

This finding was an error: the `has_rate = 0` result came from querying **`payment_transactions`**, not `payment_intents`. Corrected data:

```sql
SELECT currency, count(*) AS rows, count(exchange_rate) AS has_rate,
       min(exchange_rate), max(exchange_rate)
FROM payment_intents GROUP BY currency;
--  USD | 1163 | 1120 | 17580.00 | 18500.00
--  IDR |   57 |   56 | 17580.00 | 18500.00
```

**`payment_intents.exchange_rate` is populated.** The chain works end to end: NestJS sends `exchange_rate` → `server.go:84` reads `req.ExchangeRate` → `CreateIntentCommand.ExchangeRate` → `NewPaymentIntent`. There is no audit gap on intents.

What remains is much smaller: **`payment_transactions.exchange_rate` is NULL on all 1177 rows** — the column exists and is never written. Likely vestigial, since the parent intent already carries the rate. Worth deciding whether to populate it or drop the column, but it is **not** the serious issue this section originally claimed. ~43 USD intents have a NULL rate, almost certainly rows predating migration 012.

### 5. Lower-priority issues found (not investigated deeply)

- **Zero DB transactions anywhere.** `db.Transaction`, `Begin()`, `FOR UPDATE` all return zero grep matches across `internal/`. Intent/transaction status updates are sequential `Update()` calls — a crash between them leaves inconsistent state.
- **Webhook auth is non-constant-time** string compare. Midtrans: SHA-512(`orderID+statusCode+grossAmount+serverKey`) at `midtrans_gateway.go:184-192`. Xendit: static `x-callback-token` equality at `xendit_gateway.go:151-157`. Neither has replay/nonce/timestamp protection or a delivery-ID dedup table.
- **State machine is informal** — transitions are ad-hoc `if/else` in `confirm_intent_handler.go` and `payment_handler.go`. No transition table, no guard function.
- **Domain entities carry GORM struct tags** (`gorm:"primaryKey;type:uuid"` in `payment_intent.go`), so the layering is "Clean Architecture-inspired," not actually infra-agnostic. Worth knowing before describing it as hexagonal anywhere public.
- **Stripe and PayPal gateways are stubs** with literal `// TODO: Implement Verify, Webhook later` comments.
- **No `context.WithTimeout`** in non-test code. Event publishing on manual-review approval is fire-and-forget (`go func()` at `payment_handler.go:468`) with errors swallowed.
- **Tests:** 10 test files vs 55 source files (~18%), 1693 test LOC. No integration tests against real Postgres/RabbitMQ.

## Decisions made

- **Fix before publicising.** `github.com/hdpolover/ybb-platform` is public and linked from the portfolio, so any claim about this service is two clicks from verification. The portfolio copy about the Go service is on hold until these are addressed.
- **`int64` minor units over `shopspring/decimal`** for the money fix — the proto already speaks `int64` minor units, so this deletes a cast rather than adding a type. Wrinkle: the 83 fractional fee rows need `×100` and round, losing sub-cent fee precision. That's arguably correct (sub-cent fees aren't real money) but it's a one-way door.
- **No proto change needed** for idempotency — metadata is out-of-band and the server already reads it.

## Open threads

1. ~~The intent-reuse design decision~~ — **RESOLVED.** Option A implemented, in Go rather than NestJS. See *Work completed*.
2. **Cannot key idempotency on `intent_id` alone** even after reuse. A legitimate retry after a *failed* payment with a different method hits `ValidateIdempotencyRecord` → hash mismatch → `ErrIdempotencyConflict`, permanently poisoning the intent. Failed records may need TTL/expiry, or the key needs an attempt dimension. **Still unresolved — this blocks step 4 (wiring the key), not the intent-reuse work already done.** Note the client-generated-key model (old option B) does not have this problem: a genuinely new attempt gets a new key, which is correct Stripe semantics.
3. ~~Two paths reach `processPayment`~~ — **RESOLVED.** `/payments/intents/:id/confirm` (`payments.controller.ts:51`) has **no caller** in `ybb-program-next`, admin-dashboard, or anywhere else grepped. Only `/portal/payments/:id/confirm` (`portal.controller.ts:262`) is live, and it is the sole `createIntent` caller. The `payments.controller.ts` path takes an existing `intentId` and never creates one, so it has no duplicate-intent bug — it is only missing the idempotency key. Decide whether it is dead code worth deleting.
4. **Deploying the 019 migration is a live-traffic decision.** Migrations run **automatically at server startup** (`cmd/server/main.go:116` → `persistence.RunRawSqlMigrations`) and failure is `logger.Fatalf` — a bad migration does not roll back, it prevents the service from starting. The runner applies each file in a single `db.Exec`, so Postgres's implicit transaction makes 019 atomic (dedupe + index commit together or not at all), and `schema_migrations` prevents re-application. Still: 019 soft-deletes ~576 live intent rows and adds a constraint the **currently-deployed code violates** — if the deploy is rolling rather than recreate, old containers creating a second open intent will get a 23505 and surface a 500 to the user until they cycle out. Confirm Dokploy's deploy mode for `ybb-prod-payment` (appears to be a single container, so likely recreate = no overlap window). **Take a DB backup first regardless.**
5. **Deploy path otherwise unknown.** Service runs as `ybb-prod-payment` on ybb-vps (Dokploy, cmd `./main`, workdir `/root/`, Go 1.24.13 — note local toolchain is 1.25.6).
6. **Traffic is live** — intent count moved 1215 → 1220 during this session. Any row-count assertion here is a snapshot, not a constant.
